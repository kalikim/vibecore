# Vibecore Security Model

Status: Draft 0.1

Vibecore helps developers avoid common configuration, dependency, credential, and
deployment mistakes. It does not guarantee that an application is secure and does
not replace code review, testing, dependency auditing, penetration testing, or a
professional security assessment.

## Security objectives

Vibecore is designed to:

- prevent secrets from entering manifests, plans, logs, and generated workflows;
- make application and infrastructure mutations reviewable before execution;
- reduce accidental execution of untrusted package lifecycle scripts;
- detect unsafe or unexplained dependency changes;
- block destructive production migrations without policy evidence;
- scope agent actions to declared capabilities and permissions;
- preserve enough evidence to understand what changed and why;
- reject stale plans when relevant repository state changes.

## Threat boundaries

Vibecore operates across four trust boundaries:

1. The local repository and files generated by humans or coding agents.
2. Local programs, package managers, containers, and development services.
3. Remote systems such as GitHub, deployment providers, and secret stores.
4. Coding agents connected through a terminal, editor extension, or MCP server.

Every operation crossing a boundary must declare its required filesystem, process,
network, and secret access.

## Secret handling

Manifests contain secret contracts and source references, never secret values.
Values are resolved immediately before an approved action and passed only to the
process that needs them.

Vibecore will check:

- staged and generated files for known credential patterns;
- `.env` files and secret-bearing file names against `.gitignore`;
- GitHub workflows for hardcoded secret-like values;
- logs and action results through structural and known-value redaction;
- public-prefixed variables, such as `NEXT_PUBLIC_` and `EXPO_PUBLIC_`, for values
  that appear to be confidential;
- manifests and state artifacts for fields that should be references.

Redaction is defense in depth, not permission to print secrets. Adapters must avoid
returning secret values in the first place.

## Dependency and package safety

Package installation is a code-execution boundary because dependencies may run
lifecycle scripts. The planned dependency workflow will:

- show direct package additions and removals before installation;
- surface similarly named packages and possible typos;
- report registry, publisher, age, maintenance, and provenance signals when available;
- show packages that request lifecycle scripts;
- use lockfiles and frozen installs in CI;
- support a policy allowlist for required build scripts;
- run vulnerability and license checks through selected ecosystem tools;
- record the resulting lockfile digest in the action result.

Vibecore will not claim that a package is safe solely because no known advisory exists.

## Plans and approvals

Discovery, observation, validation, and planning are read-only. A plan includes the
repository fingerprint, target environment, proposed actions, permissions, risks,
policy decisions, and a content digest.

Before execution, Vibecore confirms:

- the plan digest is unchanged;
- relevant files have not changed;
- the target environment is explicit;
- required approvals are present;
- secret references can be resolved;
- destructive database actions meet backup policy;
- the adapter still supports the requested operation.

Production is never inferred from the current Git branch alone.

## Agent safety

The planned MCP server will expose bounded tools, not a generic unrestricted shell.
Examples include:

- `project_diagnose`
- `deployment_plan`
- `migration_review`
- `environment_check`
- `preview_deploy`

Read-only tools can be used without mutation approval. Mutating tools create a plan
and return it for review. The agent cannot convert a denied action into an allowed
one by changing natural-language instructions.

## Database safety

Prisma remains responsible for generating migrations. Vibecore adds orchestration
and policy around it:

- classify additions, removals, and type changes;
- detect drift between schema, migrations, and observed database state;
- require a backup policy for destructive production changes;
- separate migration generation from production application;
- record migration identity with the release;
- stop deployment when migration outcome is uncertain.

## GitHub and deployment safety

Generated workflows should use pinned action versions, minimal token permissions,
protected environments, secret references, concurrency controls, and explicit
deployment targets. Preview and production credentials should remain separated.

Deployment succeeds only after the configured health checks pass. An adapter must
state whether it supports rollback; Vibecore will not present a simulated rollback
when the provider cannot restore a previous release.

## Vulnerability reporting

A private reporting channel and coordinated disclosure policy must be established
before the first stable release. Until then, suspected vulnerabilities should not
include credentials, tokens, or exploitable production details in a public issue.
